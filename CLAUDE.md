# CypherPanel

Self-hosted PaaS unifying the best of Coolify and Dokploy on a desired-state, agent-based architecture. Go control plane (`cypherd`) + Go agent (`cypher-agent`) + PostgreSQL; React UI embedded as static assets.

**Current status:** Phase 1 (control-plane ↔ agent handshake) complete — see the evidence note in `docs/roadmap.md`. Phase 2 (deploy vertical slice) is built and proven end-to-end against real Docker + Traefik (integration CI: `deploy`, `deploy-resilience`): git → build → health-gated rollout → routed at its domain through the managed Proxy (`docs/features/routing-and-tls.md`), webhook deploys, SSE logs, rollback, agent-outage reconvergence, revocation — with footprints well inside the vision budgets. Deploy-key private repos (`docs/features/deploy-key-private-repos.md`), bounded runtime-log retention (`docs/features/bounded-log-retention.md`), and the `--role=builder` split + multi-server image relay (`docs/features/builder-role-and-relay.md`, ADR-008 — proven live across two Docker daemons) are implemented. Production Let's Encrypt is validated on a real domain (see the Phase 2 evidence note in `docs/roadmap.md`). With ADR-009 (Apache-2.0 license) and ADR-010 (agent auto-update mechanism) decided 2026-07-20, **Phase 2 is complete**. **Phase 3 (state-model breadth) is complete** (2026-07-21): managed databases + S3 backups/restore, preview environments, notifications (Email/Discord/Slack/Telegram), scheduled tasks (cron-in-container, ADR-011), and teams + roles — each with real-Postgres store tests and end-to-end verification. **Phase 4 (catalog and polish) is under way:** the template catalog ships 137 bundled entries — 7 hand-curated plus 130 translated from Coolify's compose library by the build-time importer `core/cmd/coolify-import` (`docs/dev/template-import.md`), every image digest-pinned. What the importer refuses, and why, is recorded per template in `docs/dev/template-import-report.md`. **Control-plane hardening** is done (`docs/features/control-plane-hardening.md`): per-agent NATS reply inboxes (closing a cross-agent read of plaintext desired state — threat-model §5.2, and the one deliberate agent/plane compatibility break), trace ids + panic recovery on every response, `GET /panel/version` with an opt-out release check, `GET /panel/logs`, two-dimension login throttling with `Retry-After` and trusted-proxy client addressing, `CYPHERD_PUBLIC_URL`, and an expired-session purge. **Agent identity and TLS** is done (`docs/features/agent-identity-and-tls.md`): agent certificates renew themselves over the mTLS channel at two thirds of their life with a fresh key and an atomic swap (revocation now denies renewal too, closing threat-model §5.2's open TTL decision at 90 days), Let's Encrypt is one panel-wide ACME account carried to every node in `DesiredState` (`GET/PUT /panel/tls`, owner) instead of a per-host env var, the proxy emits `certResolver` and the HTTP→HTTPS redirect only when a resolver actually exists — with `Application.tls_state` so the UI can say "serving over HTTP meanwhile" honestly — and the join command completes on a fresh host (the installer defaults to the latest release asset; a release panel pins the agent to its own version). **Deploy protection** is done (`docs/features/deploy-protection.md`): an Environment declares who must approve a deploy there and when deploys are refused outright, enforced once at the single point where a Deployment is born — a parked deploy is `status: awaiting_approval` with no work item published, no application status touched and no queue slot held; freeze windows are weekly, zone-aware and may wrap the week (the plane embeds `time/tzdata`), a frozen deploy/rollback/webhook answers 409 naming when it lifts, break glass is a 30-minute recorded owner override of the freeze only, and approve/reject/break-glass and the policy PUT itself are session-only so a CI token can neither open its own gate nor delete it. **The audit log** is done (`docs/features/audit-log.md`): one immutable row per sensitive action — who did what to which resource, from where, and whether it worked — written synchronously by the handler that performed it and queryable per team at `GET /api/v1/audit`. `audit_events` deliberately carries no foreign keys, because an entry must outlive everything it names (a cascade would delete exactly the evidence of a deletion, and `SET NULL` would erase the team scope that authorizes the read), and the ownership chain is snapshotted inside the `INSERT` from whichever link the handler knew. Reading it needs no role gate — scope *is* the authorization: your teams' rows, your own actions wherever they landed, plus the panel-level rows for a panel admin, with a `team_id` you do not belong to answering an empty page rather than a `403`. Details carry key names and reasons, never a secret value. It closes threat-model §5.1's "full audit log" control and §5.3/§8.1's "enrollment is an audited event" (`server.enrolled`, previously a log line), makes `ConfirmDestructive`'s "audit-logged with your name" true, and takes the approval and break-glass decisions deploy protection deferred to it. Automated mutations are in it too: a preview environment that a pull request spawns and a close or the TTL sweeper reclaims writes `environment.created`/`environment.deleted` with a `system` actor, so an environment cannot come and go unrecorded. `CYPHERD_AUDIT_RETENTION` (90d, `0` = forever) is swept hourly in bounded batches by one owned goroutine. **Team invitations and access requests** are done (`docs/features/invitations-and-access-requests.md`): an admin invites an address, the invitee gets a single-use seven-day link, chooses their own password and lands signed in — closing the "invitations by email" non-goal that teams-and-roles, panel-mail and first-run-setup each deferred. Only `sha256` of the secret is stored, the wire token is `<invite id>.<secret>` so the lookup is an indexed read and the secret is compared in constant time before anything is spent, and the accept URL is readable exactly once (in the create response, whether or not mail went out — a panel with no SMTP still gets a link to hand over). Accepting for an address that already has an account runs the ordinary sign-in path, so its current password and second factor still apply: an invitation is never a password reset. The mirror image is the **Access Request** the 403 screen opens — a member asks this team's owners for a higher rank with a message; granting applies through the existing member-role path, so the last-owner guard holds, and grant/deny are session-only because an API token inherits its owner's role. The rank is checked when a permission is created, never when it is spent; the two public routes are throttled by client address and answer one undifferentiated 404 for unknown/wrong-secret/expired/revoked/spent; removing a member revokes the invitations they issued. The inbox gained its third scope (`team_id`) for `access.requested` / `access.granted` / `access.denied` / `invite.accepted`. A read-only `viewer` role stays out of scope — it belongs to granular RBAC behind its own ADR. **Container registries** are done (`docs/features/registries.md`): ADR-008's path 3, and nothing more — a team-scoped, sealed credential an application may pull its image (or its private base image) through, and a build may push its result to, while the rollout still runs the local build or the relayed one, so no registry is ever required. The credential is unsealed in exactly one place, the scheduler at work-build time, exactly as the deploy key is; nothing is cached, so rotating or deleting one takes effect on the next deploy and no `docker login` state is left on a builder. `can_pull`/`can_push` are checked when a registry is ATTACHED, not when it is spent, so a pull-only credential named as a push target is a 400 rather than a 403 from the registry after a five-minute build — and a registry in another team answers the same "no such registry" as one that does not exist, so an application's config screen is not a way to enumerate other teams' credentials. `ON DELETE RESTRICT` on both application columns: a credential cannot vanish from under a deploy, and the 409 is backed by `used-by`, which NAMES the applications. On the wire it is two additive proto messages and three fields (`buf breaking` clean); the daemon's two different headers — `X-Registry-Auth` for a pull, `X-Registry-Config` for a build's base image — share one encoder in `pkg/registryauth`. A named registry the plane cannot resolve fails the deploy rather than pulling anonymously, and a failed push fails the deployment rather than reporting success for an image that is not where it was promised to be. **Deployment control** is done (`docs/features/deployment-control.md`): the four things an operator can do about a deploy or an application once it is already moving. `POST /deployments/{id}/cancel` is the PANEL stopping waiting, not a remote kill — ADR-002 gives the plane no way to stop a running build, so a build in flight finishes and its image is reclaimed by desired-state GC because nothing desires its revision; it works while queued, awaiting_approval, building or distributing, and answers 409 once `rolling_out` because desired_revision_id has moved by then and cancelling would leave the panel claiming it abandoned what every agent is still converging on (the honest recovery is a rollback, and the 409 says so). It adds no sixth status, for the reason deploy protection already recorded when it declined one for rejection, and announces nothing to notifiers or webhooks: a cancellation is a person's decision, not an infrastructure failure. `POST /applications/{id}/restart` is a restart expressed as DESIRED STATE rather than a verb the agent obeys (ADR-005): a fresh `restart_token` rides on the AppSpec and is stamped on the container, so a new token is drift the existing recreate path closes — the replacement starts alongside, health-gates, takes the route and only then does the old one drain, so a restart is zero-downtime for the same reason a deploy is, and converging twice afterwards mutates nothing. It is not a deploy (no revision, no build, no deployment row, desired revision unmoved — restarting a wedged container must not silently ship an hour-old edit) and a freeze window does not gate it, because a freeze exists to stop new code shipping and a restart ships none. Both log streams take `?since=` (a Go duration or an RFC 3339 instant, anything else a 400 rather than a silent fall back to the whole window). And `app.crashed` / `app.recovered` join the SUBSCRIBABLE taxonomy — one edit, so notifiers, outbound webhooks and the inbox gain them at once — fired on the TRANSITION `running`→`error` and `error`→`running` only: requiring the previous status to be exactly `running` is what keeps a failed rollout (which reports `error` while the OLD container still serves) out of the channel, and `degraded` never fires because a channel that pages on "serving, with something wrong" gets muted. **Compose Stacks** are done (`docs/features/compose-stacks.md`): the third Resource in an Environment, beside Application and Managed Database, and the honest home ADR-007 named for "I have a compose file and want it run". The FILE is the desired state, which is how it stays inside ADR-005: the plane stores a file, ships a file and never sends a command, while the agent owns one fixed `docker compose up -d --remove-orphans --wait` of its own — and `up -d` is a convergence, not an imperative verb, so converge-twice mutates nothing (guarded by an on-host revision marker plus a running-services check, so the 60s drift pass does no work and a service that died since is still re-upped). Absence means remove in two nested senses: `--remove-orphans` drops a service deleted from the file, and a `cypher-` project no spec names is brought down — never with its volumes, the same rule databases follow. It is deliberately NOT a Deployment: a stack has no build and no distribute stage, so the pipeline's three-stage machinery would be ceremony around one converge — deploying mints a ComposeRevision and re-points desired state, the revision list IS the history, and rollback re-points it back. Routing cannot use the file's own Traefik labels, because the managed Proxy runs the file provider only (ADR-004 keeps the socket out of Traefik), so a stack names WHICH service and port answers and the plane emits the same fragment an Application gets, with the Proxy attached to whatever network compose actually created. Two directives are refused and the reasons are recorded — `build:` (there is no builder on a target host; ADR-008's build story is a builder-role agent and a relay) and `container_name:` (it collides across environments on one server) — while `privileged`, host mounts, `cap_add` and host networking are ALLOWED, because they are exactly what the ~130 catalog entries need. That widening is paid for with rank rather than pretended away: writing the file is team admin, deploying one a member, every mutation audited by fact-of-change and never by content (threat-model §5.15). Secrets never live in the stored file: sealed rows reach compose through an env file the agent writes 0600 and removes on every exit path. **Nixpacks pack builds** are done (`docs/features/pack-builds.md`): the framework-build case `build-detection.md` §6 deferred on exactly the condition it named. The integration is deliberately shallow — `nixpacks build <dir> --out <dir>` WRITES a Dockerfile and does not build, so the ordinary tar-and-build path consumes it and there stays one place labels are stamped, one place a private base image's credential applies and one place logs stream from. `auto` now prefers the pack over static when a language manifest is present (a Vite repo has both, and serving its SOURCE index.html shipped unbuilt TypeScript — that looked like a successful deploy and was not), but ONLY where the binary is actually installed, so a builder that has not opted in resolves exactly as it did before. Application env vars are deliberately NOT passed to the pack: Nixpacks takes them as `--env` argv, which is world-readable through `ps`, and a sealed value must not reach the process table — configuration comes from `nixpacks.toml` in the repo instead. **Railpack is deliberately not shipped**: it is a BuildKit *frontend*, so it needs a second build transport (buildx or a BuildKit session) beside the classic `/build` endpoint, which is its own decision — and the same transport is what multi-arch builds and cache mounts need, so it is worth doing once for three reasons rather than guessed at here. Still open in the phase: named application databases, dashboard, terminal, observability, design system, CLI, the audit page itself (canvas 3g) — plus ADR-010's implementation alongside the release pipeline.

## Hard rules

1. `../coolify` and `../dokploy` are **read-only references**. Port logic and schemas via the extraction maps in `research/` — never copy code. Dokploy is partly proprietary-licensed: check per directory before extracting.
2. Architectural decisions live in `docs/adrs/` and are **not re-litigated** in implementation work. Changed circumstances → write a superseding ADR.
3. Every feature must be expressible as desired state (ADR-005). No imperative "poke the server" paths.
4. No feature ships UI-only — API first, always.
5. Use `docs/glossary.md` vocabulary in code identifiers, API names, and UI copy. "Destination" is banned.
6. Follow `ENGINEERING.md` (code rules) and `docs/product/ui-principles.md` (UI rules) — they are binding, not advisory.
7. Docs: no stub files; one topic, one home; feature specs (`docs/features/`) are written just before implementing, 3–8 pages.
